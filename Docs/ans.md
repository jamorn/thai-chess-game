(ก) King Hunt ถูก Lazy-eval ตัดทิ้งหรือไม่ / ถูกเรียกใน QS หรือไม่?
คำตอบ: "ไม่ถูกตัดทิ้ง และถูกเรียกใน QS อย่างสมบูรณ์" (นี่คือจุดที่ออกแบบได้ถูกต้องที่สุดแล้ว)
เหตุผล:
ในฟังก์ชัน evaluate() เราเรียก evaluateStatic() ก่อน ที่จะเช็คว่า Math.abs(material) > LAZY_EVAL_THRESHOLD
ภายใน evaluateStatic() เราใส่ Logic King Hunt ไว้ หลังจาก คำนวณ Material + PST แล้ว
ผลลัพธ์: คะแนนจาก King Hunt จะถูกบวกเข้าไปในตัวแปร score (หรือ material) ก่อนที่จะถูกนำไปเทียบกับ Threshold 450
ความหมาย: แม้เกมจะเข้าสู่สถานะที่ฝ่ายหนึ่งนำอยู่ 500 คะแนน (เช่น ได้เรือมา) Lazy Eval จะตัดการคำนวณ Mobility ที่ใช้ทรัพยากรสูงทิ้ง แต่จะยังคงรักษาคะแนน King Hunt ไว้ เพื่อให้ AI ยังคงเดินบีบขุนศัตรูเพื่อรุกจนต่อไป ไม่หยุดเดินกลางคัน
ใน QS: เนื่องจาก QS เรียกใช้ evaluateStatic() โดยตรง King Hunt จึงทำงานในจังหวะกินต่อเนื่องด้วย ช่วยให้ AI ไม่เดินหมากที่ปล่อยให้ขุนศัตรูหลุดจากการบีบคั้น
(ข) ทำไมต้องแยก "2 ส่วน" (Edge Distance + King Proximity)?
คำตอบ: เพราะการรุกจน (Checkmate) ในหมากรุก ต้องใช้ 2 องค์ประกอบนี้ "ทำงานร่วมกัน" ขาดอย่างใดอย่างหนึ่งไม่ได้
ลองจินตนาการฉากจบเกม เรือ + ขุน vs ขุนตัวเดียว:
ถ้ามีแค่ Edge Distance (บีบติดขอบ): AI อาจจะเดินเรือขึ้นลงเพื่อบีบขุนศัตรูให้ติดขอบ แต่ขุนของ AI เองยังยืนอยู่ไกลคนละฝั่งกระดาน ผลคือ ขุนศัตรูอาจจะหนีไปมาในแนวขอบได้อย่างไม่มีที่สิ้นสุด (หรืออาจนำไปสู่ Stalemate/เสมอเพราะเดินไม่ได้แต่ไม่ถูกรุก)
ถ้ามีแค่ King Proximity (เดินเข้าใกล้): AI อาจจะเดินขุนตามต้อยๆ ขุนศัตรูที่อยู่กลางกระดาน โดยไม่พยายามผลักดันให้ไปติดขอบเลย ซึ่งจะทำให้รุกจนไม่ได้ เพราะขุนศัตรูยังมีที่หนี 360 องศา
เมื่อมีทั้งคู่: AI จะเข้าใจว่า "ต้องเดินเรือเพื่อบีบขอบ (Edge) และ ต้องเดินขุนของเราเข้าไปประชิด (Proximity/Opposition) เพื่อตัดทางหนี" นี่คือสูตรสำเร็จของการรุกจนในฉากจบเกมครับ
(ค) มันเสี่ยงทำให้ขุนของ AI โผล่ออกมาเสียเองมั้ย (ตอนเราอ่อนกว่า)? ⚠️ (จุดสำคัญที่สุด)
คำตอบ: "เสี่ยงครับ และ AI VS Code วิเคราะห์ได้ถูกต้อง 100%"
สถานการณ์สมมติ:
ฝ่ายดำมี ขุน + เรือ (ได้เปรียบมหาศาล)
ฝ่ายแดง (AI) มีแค่ ขุน (เสียเปรียบ)
หากใช้โค้ดเดิม: AI แดงจะได้คะแนนบวกเมื่อเดินขุนเข้าไปใกล้ขุนดำ (KING_PROXIMITY_WEIGHT)
ผลลัพธ์: AI แดงจะ "เดินขุนเข้าไปหาตาย" เพราะคิดว่าเป็นเรื่องดี ทั้งที่ความจริงแล้ว การอยู่ห่างๆ ไว้ต่างหากที่จะยืดเกมและหาทางเสมอได้
🛠️ วิธีแก้ไข: เพิ่มเงื่อนไข "Material Safety Check"
เราจะบอก AI ว่า "การเดินขุนเข้าประชิด (Proximity) จะให้คะแนนก็ต่อเมื่อ เราไม่ได้เสียเปรียบมหาศาล เท่านั้น" (เช่น คะแนนรวมไม่ติดลบเกิน 150 คะแนน ซึ่งประมาณว่าเสียไม่เกิน 1 เบี้ย/เม็ด)
ให้แก้ไขบล็อก if (isEndgame) ในไฟล์ src/engine/Evaluator.ts (ฟังก์ชัน evaluateStatic) เป็นดังนี้ครับ:
  // ✅ ใหม่: Endgame King Hunt Heuristic (ใส่ที่นี่เพื่อให้ทำงานเสมอ)
  if (isEndgame) {
    const enemySide = aiSide === Side.RED ? Side.BLACK : Side.RED;
    const enemyKingPos = this.findKing(board, enemySide);
    const myKingPos = this.findKing(board, aiSide);

    if (enemyKingPos && myKingPos) {
      // 1. Edge Distance: บีบขุนศัตรูติดขอบ (ทำเสมอ ไม่ว่าได้เปรียบหรือเสียเปรียบ เพื่อหาทางชนะหรือเสมอ)
      const edgeDistance = Math.min(
        enemyKingPos[0], 7 - enemyKingPos[0],
        enemyKingPos[1], 7 - enemyKingPos[1]
      );
      score += (3 - edgeDistance) * this.EDGE_DISTANCE_WEIGHT;

      // 2. King Proximity: เดินขุนเราเข้าใกล้ขุนศัตรู (Opposition)
      // ⚠️ แก้ไข: ตรวจสอบว่าเรา "ไม่ได้เสียเปรียบมหาศาล" ก่อนที่จะเดินขุนเข้าประชิด
      // ถ้า score ติดลบมาก (เช่น เสียเรือไป -500) การเดินขุนเข้าใกล้คือ "เดินเข้าหาตาย"
      // เราตั้ง Threshold ไว้ที่ -150 (เสียเปรียบไม่เกิน 1 เบี้ย/เม็ด) จึงจะกล้าเดินขุนเข้าประชิด
      if (score >= -150) {
        const kingDist = Math.max(
          Math.abs(enemyKingPos[0] - myKingPos[0]),
          Math.abs(enemyKingPos[1] - myKingPos[1])
        );
        score += (7 - kingDist) * this.KING_PROXIMITY_WEIGHT;
      }
    }
  }
